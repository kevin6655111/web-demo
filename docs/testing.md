# 測試策略

四層，各自回答不同的問題。上層慢但真實，下層快但抽象 —— 兩者都需要。

| 層 | 數量 | 速度 | 回答什麼問題 |
|---|---|---|---|
| 前端單元 | 33 | ~2s | 判斷邏輯對不對(顏色、門檻、去重、格式) |
| 後端單元 | 25 | ~1s | 守衛、冪等、回應信封的行為對不對 |
| 端到端 | 63 | ~3m | 整條路徑在瀏覽器裡真的會通嗎 |
| 手動 | — | — | 視覺與地圖互動 |

## 前端：判斷與渲染分開

判斷邏輯全放在 `presenters/`(純函式)，元件只負責畫。

於是最有價值的測試不需要 DOM、毫秒級跑完；元件測試只留下
「非渲染就驗不到」的少數幾件事：無障礙標籤、條件顯示、動畫終值。

```bash
yarn test           # 跑一次
yarn test:watch     # 監看模式
```

**不測樣式與版面** —— 那種測試每次改設計都會壞，卻抓不到真正的問題。

## 後端：守衛與冪等

用假的 Redis 與 ExecutionContext 測守衛與攔截器的行為。
四種冪等情境都各有一個測試釘住：第一次執行、重送回放、內容不同擋下、失敗放鎖。

```bash
yarn test:api
```

## 效能：用查詢數而不是碼錶

「感覺變快了」不是證據，本機的資料庫沒有網路延遲，碼錶量到的差距會比實際小一個數量級。
可以數的是**送出幾筆查詢、開了幾個交易** —— 那個數字乘上往返延遲才是使用者的體感。

```bash
# 讓 Postgres 記下每一筆語句
docker exec patrol-postgres psql -U patrol -d patrol_demo \
  -c "ALTER SYSTEM SET log_statement='all'" -c "SELECT pg_reload_conf()"

# 用兩個標記查詢框住要量的區間，再從容器日誌裡數
docker logs patrol-postgres --tail 4000 | grep -c 'START TRANSACTION'
```

批次巡查單狀態變更（50 筆）改善前後：

| | 交易 | 查詢 | 本機耗時 |
|---|---|---|---|
| 逐筆寫歷程 | 51 | 354 | 0.39s |
| 批次寫歷程 | 2 | 10 | 0.045s |

本機快了 8.6 倍；跨網段時差距是 350 趟往返對 10 趟。

**量完記得關掉** `log_statement` —— 開著會讓資料庫日誌長得非常快。

## 打包前的驗證

混淆會改寫每一個 `.js`，**改壞了只有在啟動時才看得出來** ——
所以 `release-offline.yml` 在打包前真的把混淆後的後端跑起來問一次健康檢查。

```bash
yarn build:api:prod
RUN_MIGRATIONS=false PORT=3018 node -r ./apps/api/register.js apps/api/dist/main/api.js
curl -sf http://localhost:3018/api/health
```

連不上資料庫的錯誤與混淆壞掉的錯誤長得完全不一樣，所以這一步不需要資料庫。

## 端到端：Playwright

測的是「整條路徑會不會通」——前三層都測不到瀏覽器裡真的發生了什麼。

```bash
yarn test:e2e                # 需要服務先跑起來
yarn workspace @road-patrol/e2e test:ui   # 有介面的除錯模式
yarn workspace @road-patrol/e2e report    # 看上次的報告
```

涵蓋：登入與權限過濾、憑證過期自動踢出、導覽、案件查詢與歷程、
**表單（詳情、編輯、派工、管理頁六種新增）**、地圖渲染與工具、圖層疊看、
即時推播（從 API 建案件 → 看瀏覽器有沒有自己更新）、冪等重送、
**巡查單與派工單的約束**（有派工單時刪不掉、已回報要先撤回、復原回到刪除前的狀態）。

**約束用 API 驗，畫面用瀏覽器驗**。要在畫面上製造出「已回報的單刪不掉」
需要好幾步；用 API 直接走完，規則壞掉時失敗訊息會直接指出是哪一條。
反過來，「勾選框一按就打開詳情」這種只有真實 DOM 才看得出來。

**不要在測試裡寫死資料庫 id**。公司 id 依建立順序而定，而平台層那一筆是
migration 補的 —— 全新的資料庫與長期運行的資料庫，同一個代碼會落在不同的 id 上。
寫死 id 的測試只在寫它的那台機器上會過。

**登入只做一次**：每支測試各自登入的話，連續失敗 5 次會觸發帳號鎖定 ——
那是系統該有的行為，但會讓整批測試從第六支開始全紅。

失敗時自動留下截圖、影片與 trace：

```bash
npx playwright show-trace e2e/results/artifacts/<測試名>/trace.zip
```

## 這些測試抓到過的真 bug

寫下來是因為它們說明了每一層的價值：

| Bug | 哪一層抓到 | 為什麼下層抓不到 |
|---|---|---|
| BullMQ `jobId` 含冒號 → 派工 500 | 手動 API 測試 | 型別檢查看不出字串格式限制 |
| 全域守衛擋掉微服務事件 → WebSocket 從不推播 | Playwright | 後端單元測試不會跨行程 |
| 側邊欄蓋住內容、蓋住的區域點不到 | Playwright | 沒有真實版面就沒有遮擋 |
| `>>` 有號位移導致路名變成「民生路undefined」 | 手動 + 回歸測試 | 只在雜湊值超過 2³¹ 時發生 |
| MVT 圖磚沒轉投影 → 永遠回空圖磚 | 手動 API 測試 | PostGIS 不會報錯，只是安靜地回空 |
| 圖片檢視器按「放大」卻跳出案件詳情 | Playwright | React portal 沿元件樹冒泡，不是 DOM 樹 |
| 簽名網址用容器主機名，瀏覽器連不到 | 手動驗證簽名網址 | 後端自己打得通，只有瀏覽器打不通 |
| 面板渲染兩次 → 資料抓兩遍、圖層登錄兩遍 | Playwright | 畫面看起來正常，只有網路面板看得出來 |
| 詳情對話框翻頁按了不動 | Playwright | 索引算錯，但沒有任何錯誤訊息 |
| 單號用「筆數 + 1」→ 序號有缺口時撞號 | Playwright（連續建單）| 單筆建立永遠成功，要有既有資料才撞得到 |
| 派工單改多人後，儀表板的逾期清單 500 | Playwright（導覽全走一遍）| 型別檢查過得了 —— 關聯名稱是字串 |
| 復原巡查單回到初始狀態而不是刪除前 | Playwright（走完整條流程）| 每一步單獨看都正確，錯的是中間漏寫的歷程 |
| 缺件篩選的 `TOTAL` 是篩選前的數字，一頁 50 筆只回 44 筆 | 手動比對回應 | 每一筆資料都正確，錯的是「一共幾筆」|
| 前後端的材料中文對不上（冷拌瀝青／冷瀝青）| 抽掉重複之後編譯就過不去 | 兩邊各自都是對的，只有放在一起看才看得出來 |

最後一項特別值得記住：**不報錯的失敗最難查**。
