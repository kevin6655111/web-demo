# 移植報告：web_server → web-demo

這份文件記錄**搬了什麼、沒搬什麼、以及為什麼**。

寫下來的理由是：半年後有人打開這個 Demo，會問「這個系統是不是少了什麼」。
沒有這份清單的話，答案只能靠翻程式碼推測，而推測出來的答案通常是錯的。

> web-demo 是公開的示範專案，所有資料都是合成的（示範工程公司、示範市政府建設局）。
> 任何識別得出真實客戶的東西都不在裡面 —— 那不是疏漏，是這份移植的第一條規則。

## 一句話總結

**業務主線完整搬過來了，客戶專屬的東西一個都沒搬。**

### 移植時順手修好的

這幾個是 web_server 的既有行為，搬過來時發現不對而改掉的：

- **每日檢查看不到沒上傳的車** —— 原本以案件為主表統計，
  一台出了車卻一筆都沒上傳的車根本不會出現在清單上，而那正是要抓的第一種異常。
  改成案件與軌跡 `FULL OUTER JOIN`，三種情況（只有案件／只有軌跡／兩邊都有）各自成列。
- **行政區判定在邊界上會失敗** —— `ST_Contains` 不含邊界，
  座標剛好落在兩區交界時三個欄位全是 null。改用 `ST_Intersects` 並加上確定性排序。
- **車機狀態會遺失更新** —— ECU 與影像幀同時抵達時，
  兩邊都做「讀整包 JSON → 改一個欄位 → 寫回」，後寫的會蓋掉前一個。
  改用 Redis hash 的 `HSET`／`HINCRBY`，各改各的欄位。

## 沒搬的，以及為什麼

### 一、客戶專屬（搬過來就是把客戶的東西放進公開專案）

| 模組／功能              | 是什麼                       | 為什麼不搬                                           |
| ----------------------- | ---------------------------- | ---------------------------------------------------- |
| 某案場的無人機巡查對接  | 一整套獨立的案件與航跡結構   | 綁定該案場的無人機平台帳號體系                       |
| `ws-client`             | 連到客戶中央伺服器的中繼     | 對端位址與協定是該客戶的內部系統                     |
| `geo-ship` `project-ship` | 特定客戶的圖資／標案同步    | 對接的是對方的內部系統                               |
| 某縣市專用的破壞資訊欄位 | 該縣市要求的額外表單欄位    | 單一客戶的表單，不是共通的領域概念                   |
| 某廠商格式的報表        | 一種客製版型的報表           | 版型與欄位是那一家的規格                             |
| 兩家廠商的 App 收案對接 | 兩支客製的 App 收案端點      | 各自的協定與欄位，不是共通介面                       |
| LINE bot                | LINE 通知                    | 綁定客戶的官方帳號與好友名單                         |

**這一類不是「暫時沒空搬」，是不該搬。**

### 二、範圍外（使用者明確排除）

| 模組         | 是什麼                     | 備註                                              |
| ------------ | -------------------------- | ------------------------------------------------- |
| `ai-studio`  | 標註與模型訓練平台         | 八張資料表的獨立子系統，本身就是另一個產品        |
| AI 智能助理  | 地圖上的對話式查詢         | 需要接大型語言模型，與這個 Demo 要展示的東西無關  |
| 人行道案件   | 人行道破壞的獨立案件型別   | 與車道案件是平行的一整條流程                      |

### 三、示範專案不需要的基礎設施

| 模組           | 為什麼不搬                                                       |
| -------------- | ---------------------------------------------------------------- |
| `webhook`      | 對外推送需要一個真的接收端；Demo 沒有                            |
| `log-recorder` | 日誌走 Loki／Promtail（`monitoring/`），不再自己寫一份           |
| `audit-log`    | 改成 `@Audit()` 攔截器 + 結構化日誌，不另存一張稽核表            |
| `http`(部分)   | 只搬了回應信封、守衛與攔截器；客製的 HTTP 客戶端沒有用到         |

### 四、刻意改變作法的

| 項目              | web_server 的作法                  | web-demo 的作法                                            |
| ----------------- | ---------------------------------- | ---------------------------------------------------------- |
| `init-process`    | 開機時把多份參考資料載進記憶體     | 只做環境自檢 + 把**界線圖層**預熱進 Redis（見下）           |
| 前端建置          | CRA + CRACO                        | Vite（建置 11 秒 vs 分鐘級）                                |
| 共用代碼表        | 前後端各一份                       | `packages/shared` 單一來源，前端全部由它推導                |
| 文件              | 單一份 Swagger                     | 內部／對外分流 + 一單位一把金鑰                             |
| 資料庫            | MSSQL + PostgreSQL 並存            | 只有 PostgreSQL + PostGIS                                   |

#### init-process 為什麼只預熱界線

使用者要求「初始化可以在 Redis 快取的就移過去」。實際檢視之後，
**符合條件的只有行政區界線**：

| 資料       | 一年變幾次 | 每家公司一樣嗎 | 結論                            |
| ---------- | ---------- | -------------- | ------------------------------- |
| 行政區界線 | 1          | 是             | **開機預熱**，TTL 24 小時       |
| 標案統計   | 每天       | 否             | 端點上 `remember()`，第一次查觸發 |
| 行政區凸包 | 每天       | 否             | 同上                            |
| 代碼表     | 幾乎不變   | 是             | **不快取** —— 已經是純記憶體運算，放 Redis 反而多一趟網路 |
| 道路量測   | 一年 1 次  | 是             | **不快取** —— 查詢 0.02 ms，快取省不到什麼卻多一處要失效 |

把會變動的資料也預熱，等於在開機時就先產生一批準備要過期的快取。
預熱失敗不擋啟動也不算自檢失敗 —— 唯一的後果是今天第一個打開圖台的人多等一下。

## 地圖：做了什麼、沒做什麼

| 功能           | 狀態                                                          |
| -------------- | ------------------------------------------------------------- |
| 破壞／軌跡／路段／計畫／調查點圖層 | 完整                                       |
| 行政區界線（三層） | 完整，可疊在其他圖層下當參考框                            |
| 建物量體       | **2.5D**：輪廓 + 顏色深淺表示樓高，不是真的 3D 拉伸           |
| 街景           | Mapillary（Google 需自備金鑰，沒有金鑰時誠實顯示需要金鑰）    |
| AI 智能助理    | 不做（範圍外）                                                |
| 人行道案件圖層 | 不做（範圍外）                                                |

**建物沒有做真正的 3D 拉伸**：那需要 deck.gl 或 MapLibre 這類 WebGL 繪圖層，
而這張圖台是 Leaflet（SVG）。為了一個判讀用的輔助圖層換掉整個繪圖引擎、
或多背幾百 KB 的第二套引擎，都不划算。改用顏色深淺表達樓高，
在「旁邊是透天還是大樓」這個實際要回答的問題上已經夠用，
而平面圖比斜視圖更容易對到路段位置。實際樓層數在 popup 裡。

這是取捨，不是做不到。真的需要 3D 的專案應該直接換繪圖層，而不是在 Leaflet 上疊。

## 還沒做的

誠實列出來，而不是讓人自己去發現：

- **前端的二篩計薪頁面** —— 後端的 `/sift/salary` 已完成，前端只有判讀與覆核兩個分頁
- **報表的預覽** —— 目前是產生後下載，沒有線上預覽
- **建物圖資的匯入工具** —— 目前只有合成資料；正式環境要接開放圖資的匯入流程
- **e2e 沒有涵蓋車機通訊面板** —— 它需要一個活著的 WebSocket 連線，
  而模擬器刻意繞過連線那一層（所以模擬出來的車機 `CONTROLLABLE` 為 false）
