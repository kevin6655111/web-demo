# 架構說明

## 目錄結構：四個 workspace

```
apps/web/          前端 (@road-patrol/web)     Vite + React
apps/api/          後端 (@road-patrol/api)     NestJS，六個行程共用同一份 src
  src/main/          六個進入點
  src/<領域>/        領域模組
packages/shared/   共用語彙 (@road-patrol/shared)
e2e/               Playwright (@road-patrol/e2e)
```

原本是單一 package 底下的 `src/`(前端) 與 `server/`(後端) —— 名字不對稱、
`server/src` 又是第二層 src，而且**兩邊的依賴混在同一份 `dependencies` 裡**：
後端映像檔的 production 安裝會裝進 MUI、Leaflet、Recharts 這些它一個都用不到的東西。

### packages/shared：領域語彙的唯一來源

放的是「這個系統的世界裡有哪些東西」—— 破壞類型、單據狀態、施工材料、照片分區。
它們同時是**後端的驗證清單**與**前端的下拉選項與中文標籤**。

前後端各存一份的下場不是假設，是已經發生的事：

| 項目          | 後端           | 前端                             |
| ------------- | -------------- | -------------------------------- |
| 材料 `COLD`   | 冷拌瀝青       | 冷瀝青                           |
| 材料 `OTHER`  | 不存在         | 有一個「其他」                   |
| 標案狀態      | 含 `SUSPENDED` | 少了它 —— 暫停中的標案顯示成空白 |
| 派工類型 `PC` | AI 車巡        | AI 車巡案件                      |

現在 `apps/web/src/config/vocabulary.js` **不手寫任何一份對照表**，
全部由定義推導（`labelsOf` / `colorsOf`）。後端新增一個狀態，前端自動就有。

兩個刻意的設計：

- **沒有執行期依賴**：後端在 CommonJS 裡用它、前端在 ESM 裡用它，
  多一個依賴就要同時滿足兩邊。
- **同時輸出 CJS 與 ESM**：Rollup 看不穿 CJS 的 `export *`，
  只給 CJS 的話前端建置會說「找不到這個具名匯出」。
- **色彩用語意詞不用色碼**：shared 說「這是警告」，前端才決定日夜各是什麼顏色。

## 為什麼拆成七個行程

單一 Node 行程即可承載全部功能。拆分的依據並非效能，而是**故障模式不同**。

| 行程            | 職責                      | 故障影響                   | 獨立部署的理由                     |
| --------------- | ------------------------- | -------------------------- | ---------------------------------- |
| `api`           | HTTP、WebSocket、事件訂閱 | 使用者看到錯誤畫面         | 使用者同步等待，延遲敏感           |
| `tiles`         | 圖層與向量圖磚            | 地圖空白，其餘正常         | 單次序列化數 MB，會佔用 event loop |
| `case-worker`   | 案件佇列（逆地理編碼）    | 路名未補上，案件仍存在     | 可能逾時，需重試                   |
| `report-worker` | Excel / Word 產製         | 報表停滯，其餘正常         | 單份報表佔用數百 MB                |
| `mail-worker`   | 郵件佇列                  | 通知延遲，業務流程不受影響 | SMTP 故障時長時間重試              |
| `scheduler`     | 11 支排程                 | 統計未更新                 | 僅能有單一實例                     |
| `nginx`         | 靜態檔與反向代理          | 全站無法存取               | TLS 與快取策略獨立於應用           |

合併部署的代價可量化：報表產製期間 event loop 被佔用數秒，同時段的登入請求延遲同幅上升。
拆分後，資源競爭侷限於單一行程內。

## 資料流

```
車機/App ──POST /patrol/case──▶ api ──┬──▶ PostgreSQL(寫入案件)
                                      │
                                      ├──▶ BullMQ ──▶ worker ──▶ 逆地理編碼 ──▶ 更新路名
                                      │                            └──▶ 寫入歷程(新版本)
                                      │
                                      └──▶ Redis 事件 ──▶ api(訂閱) ──▶ WebSocket ──▶ 瀏覽器看板
```

三條路徑刻意分開：

- **寫入**要快且一定要成功 → 同步做，只寫一筆
- **補資料**慢且可能失敗 → 佇列，可重試
- **通知**可有可無 → 事件，訂閱者掛掉不影響前兩者

## 單據流程

這套系統的主線是「發現 → 派工 → 施工 → 驗收」，四種單據各自一組表：

```
AI 車巡案件 (patrol_cases) ──┐
                             ├─→ 派工單 (work_orders) ─→ 施工中 ─→ 已回報 ─→ 已完工
巡查單/巡修單 (maintenances)─┘    PC 來自車巡、PD 來自巡查單
```

**分表而不是一張寬表**，因為欄位的「誰在寫、什麼時候寫」不同：

| 表                   | 誰在寫                     | 頻率                         |
| -------------------- | -------------------------- | ---------------------------- |
| 主表                 | 來源系統（車機、現場 App） | 寫入一次就幾乎不動           |
| 狀態表               | 承辦、施工人員、驗收人員   | 反覆改，而且要記「誰改的」   |
| 附屬表（取樣／回填） | 只有特定類型有             | 類型改變時整列刪掉           |
| 照片表               | 現場                       | 每個類型只留一張，重傳是覆寫 |

合併為單一資料表時，車機的高頻寫入會與承辦的編輯競爭同一列的鎖。

### 狀態不是直接寫入的

派工單與巡查單的狀態端點收三個**動作碼**，它們要先看當前狀態才知道要寫什麼：

| 動作      | 規則                                                       | 為什麼不讓前端自己算                               |
| --------- | ---------------------------------------------------------- | -------------------------------------------------- |
| 撤回 (9)  | 退一階；退到待處理／施工中這段時改由「有沒有施工人員」決定 | 規則會跟著業主的驗收流程改，兩邊各算一次遲早不一致 |
| 復原 (8)  | 回到**歷程上一個不同的狀態**                               | 前端看不到歷程                                     |
| 刪除 (-1) | 已回報／已完工不允許，要先撤回                             | 抹掉已回報過的事實是不可逆的                       |

**「有人員即施工中、無人員即待處理」是系統不變量。** 違反時，看板會顯示為有人施工，
而現場實際無人到場 —— 該狀態不會被任何流程修正。

### 刪除的守門條件

巡查單在其派工單仍有效時不可刪除，且不執行連帶刪除。
連帶刪除會在使用者未預期的情況下影響他人正在施工的派工單。

批次操作不採全有全無：被擋下的項目各自附上原因回傳。
整批失敗會迫使使用者自行判斷失敗原因，並重送其餘項目。

## 案件編號

三種單據在建立時即取號，不留待後續批次補編。編號規則：

| 單據     | 格式               | 分段                          |
| -------- | ------------------ | ----------------------------- |
| 車巡案件 | `DEMO01000123`     | 標案號 + 六位流水，不分日期   |
| 派工單   | `DEMO01PA26090001` | 標案號+類型 + 年月 + 四位流水 |
| 巡查單   | `DEMO01RA26090162` | 同上                          |

車巡案件不分日期，因其單日可達數千筆，分日後四位流水不敷使用；
人工開立的單據單月不超過四位數，分至月份可讓單號自帶時間資訊。

### 併發安全

取號由 `case_sequences` 計數器表提供，單一敘述完成讀取、遞增與回傳：

```sql
INSERT INTO case_sequences (prefix, seq_date, last_number) VALUES (...)
ON CONFLICT (prefix, seq_date) DO UPDATE SET last_number = last_number + EXCLUDED.last_number
RETURNING prefix, last_number
```

`ON CONFLICT DO UPDATE` 在該列上取得鎖，因此並行請求會依序取得不同號碼。

先前的實作為 `SELECT MAX(case_num) + 1` 後再 INSERT，兩個步驟之間存在競態，
依賴唯一鍵擋下衝突並重試。實測 200 個並行請求：

| 實作             | 成功                                  | 衝突 |
| ---------------- | ------------------------------------- | ---- |
| `MAX + 1` 後重試 | 1                                     | 199  |
| 計數器表         | 1000 個號碼、0 重複、無缺口（293 ms） | 0    |

車機採批次上傳，單次可達數十筆，重試迴圈在該情境下會退避至逾時。

批次取號以 `generate_series` 一次配發，並依前綴排序後執行 ——
多個交易若以不同順序更新同一組計數器列，將形成等待環（死鎖）。

驗證方式：`yarn seq:stress`。

## 快取

快取的成本是失效邏輯。加在不需要的地方，只是多了一處會不一致的資料。
因此依「成本是否隨資料量成長」決定，而非依「是否很少變動」。

| 對象                              | 現況                                            | 決定                                                  |
| --------------------------------- | ----------------------------------------------- | ----------------------------------------------------- |
| 代碼表 `/core/code`               | 由 `@road-patrol/shared` 常數推導，**0 筆查詢** | **不快取** —— 已是記憶體運算，走 Redis 反而多一趟網路 |
| 工務段、行政區清單                | 小表加索引，查詢 < 1 ms                         | **不快取** —— 省下的時間少於多維護一處失效的代價      |
| 導覽選單                          | 單筆小查詢                                      | **不快取** —— 與權限繫結，失效邏輯出錯即為授權漏洞    |
| 標案清單 `/project`               | 含案件統計聚合                                  | **快取 60 秒 + 寫入時清除**                           |
| 行政區界線 `/geo/district-bounds` | 凸包聚合                                        | **快取 10 分鐘**                                      |

後兩者的成本隨案件數線性成長：

| 案件數 | 標案統計 | 行政區凸包 |
| ------ | -------- | ---------- |
| 1,800  | 0.4 ms   | 15 ms      |
| 91,000 | 15 ms    | 110 ms     |

而兩者都出現在多個畫面的初始載入路徑上。

### 失效策略依資料的變動來源而不同

- **標案清單**：短 TTL（60 秒）搭配寫入時明確清除。使用者剛編輯完標案會立即回到列表確認，
  該落差他們會察覺；案件統計則持續變動，若採事件失效，快取幾乎不會命中。
- **行政區界線**：僅用 TTL。界線由案件位置推導而成，本身是粗略近似值，
  十分鐘的落差不影響其用途。

### 快取失效不能造成功能失效

`RedisService.remember()` 在 Redis 不可用時直接回退至即時計算，僅記錄警告。

這一點需要連線層配合。原本的設定為 `maxRetriesPerRequest: null` 且啟用離線佇列，
斷線時命令會**無限期排隊**而非拋出錯誤 —— 呼叫端的 `try/catch` 永遠等不到，
請求不是失敗而是卡住。實測 Redis 停止後，`/project` 直接逾時。

現行設定為 `enableOfflineQueue: false` 搭配 `commandTimeout`，斷線時立即拋錯，
由呼叫端降級。BullMQ 不共用此連線 —— 佇列必須無限重試直到連上，否則工作會遺失，
與應用層的要求相反。

登入失敗鎖定同樣採**失敗放行**：Redis 不可用時計數失效，登入照常進行。
反向選擇會讓 Redis 故障等同於全站無法登入。每次降級均記錄警告。

實測（Redis 停止期間）：`/project`、`/geo/district-bounds`、`/patrol/case`、`/auth/user/nav`
與登入全部正常回應，耗時 0.01–0.08 秒。

## 冪等性三層

車機在隧道裡收不到回應就重送。同一筆案件可能連來三次，而三次不能變成三筆。

| 層     | 機制                                            | 擋掉什麼       | 失效條件               |
| ------ | ----------------------------------------------- | -------------- | ---------------------- |
| HTTP   | `Idempotency-Key` + Redis `SET NX`              | 短時間內的重送 | Redis 被清空、TTL 過期 |
| 佇列   | BullMQ `jobId`                                  | 重複的背景工作 | 工作已完成並被清除     |
| 資料庫 | `external_id` 唯一鍵 + `ON CONFLICT DO NOTHING` | 所有情況       | 不會失效               |

**第三層是唯一不會失效的保證**；前兩層的作用在於避免重複執行已完成的工作。

同樣的想法用在別處：排程用 Redis 鎖、報表用 dedupKey、派工用一案一單的唯一鍵。

## 版本化歷程

每次案件變更寫一筆歷程，含**當下的完整快照**與**這次改了哪些欄位**。

存快照而不只存差異，是因為「要看第 30 版長什麼樣」不該需要從第 1 版重放 29 次 ——
而中間任何一筆寫壞，後面全部跟著錯。

**還原不刪除後續版本**：還原本身是一筆新版本。能被抹掉的歷程不算歷程。

歷程不只是給人看的 —— **復原功能靠它決定要回到哪個狀態**。
所以任何改動狀態的路徑都必須寫歷程，包含「別的模組改了我的狀態」：
開派工單會把巡查單轉成已派工、刪派工單會把它退回觀察中，這兩處都要留下一筆。
遺漏任一處，復原會跳回建立當時的狀態，且中間的變更不會出現在時間軸上。

## 導覽是資料

側邊欄來自資料庫的 `modules` / `features` 兩張表，依角色權限過濾後回傳。

若寫死於前端，各站台啟用不同功能時需分別維護建置產物。
程式碼裡的 `MODULE_DEF` 是「系統有哪些功能」的單一來源，啟動時同步進資料庫。

## 前端分層

```
views/       畫面：只負責渲染
presenters/  判斷：顏色、門檻、單位換算、去重
models/api/  呼叫：路徑與參數
hooks/       行為：WebSocket 重連、側邊欄設定
context/     狀態：登入者、地圖圖層登錄表
```

判斷邏輯全放在 presenters，所以最有價值的測試不需要 DOM、毫秒級跑完。

## 一張地圖、多個圖層

圖台只有一張地圖，各功能面板把圖層「登錄」進共用的登錄表。

破壞案件、軌跡、路段與巡查計畫因此可同時疊加檢視。
「某條軌跡是否行經特定破壞點」是本系統最常見的查詢需求。

每個圖層帶有 `group`（分組）與 `order`（堆疊順序）：點圖層需位於線圖層之上，否則點無法被點選。

## 已知限制

Demo 刻意不依賴外部服務，所以有幾處是「示範到位、但不是正式作法」：

- 逆地理編碼是決定性的假實作（正式系統接自架 Nominatim）。
- 行政區界線用案件的凸包近似（正式系統接 NLSC 圖資，那份有幾十 MB）。
- 資料庫備份、推播通知這類需要外部系統的排程，只做到「算出該做什麼」而不真的送出。
- 報表的 Word 版只列前 200 筆明細（超過請看 Excel）；報表尚未涵蓋巡查單。
- 巡查單還沒上圖台，目前只有列表。
- Google 街景**內嵌**需要 Maps API 金鑰（`VITE_GOOGLE_MAPS_KEY`）；
  沒金鑰時走免金鑰的外開連結，或切 Mapillary 內嵌。
- **Google 圖磚直接取用 `mt1` 不在其授權範圍內**，僅供內部比對；
  正式站台要改用官方 SDK。
- 沒有 TLS：Demo 走 HTTP，正式站台要補 certbot 與 HSTS。
- 案件的原始照片只存路徑（示範資料沒有實體檔案）；派工單與巡查單照片則是完整的上傳／預覽／刪除。
- 前端只在 Playwright（Chromium headless）驗證過，視覺細節沒有在真實桌機瀏覽器目視確認。
